# Automatic recipe photo resizing

Large JPEG, PNG and WebP recipe photos are decoded/oriented in the browser, resized to a maximum 1600-pixel edge and JPEG-compressed to a 768 KB transfer budget. Compression adapts before a further downsize if needed. Small originals already within dimension/byte limits pass through. Local files are never modified. The server still validates the actual image, corrects orientation, centre-crops to 1200×675 and stores normalized WebP without source metadata.

The selected file input receives the optimized File through DataTransfer, so normal form submission and validation behavior are preserved. Preview and progress text update after preparation. A capture-phase submit guard prevents submission while decoding without triggering the calculator's save-lock handler. Selection sequence guards prevent an older asynchronous result replacing a newer photo. If client decoding/canvas/file replacement fails, the original remains available for server processing rather than requiring a separate editor.

Resource bounds remain: browser original up to 50 MB, server fallback up to 32 MB / 80 megapixels. JPEG draft decoding reduces server memory before conversion. These limits apply to exceptional originals, not the final stored photo. Typical large camera photos are reduced before transfer to avoid proxy limits. Corrupt files/unsupported formats still receive clear errors; photos in reopened drafts or failed-save pages must still be reselected.

Validation: all 18 focused story/artwork/usage tests passed, including a 48 MP JPEG padded beyond the previous 5 MB limit saving as a small 1200×675 WebP. Node utility checks cover portrait/landscape scaling, unchanged originals, small-file pass-through, adaptive byte compression and limits. jsdom controller checks cover Save during processing, later file selection winning async races and successful submit resuming. JS syntax and whitespace checks passed. Live upload verification awaits deployment.
